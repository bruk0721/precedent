Casualty claims · clinical change detection

Catch the moment a minor claim stops being minor.

Lloyd's has published this exact gap twice: Cohort 16 named "intelligent summarisation of loss adjuster reports identifying changes between versions," and Cohort 17 asked for "predictive analytics models that flag seemingly innocuous third-party casualty claims before they develop into major losses" (both quotes verified live on Lloyd's own accelerator pages). ChangeSignal compares successive medical assessments on the same claim, flags what materially changed, and generates the specific claims-handling action each change calls for.

⚠ Every claim below is synthetic and invented for this demo. No real claimant, insurer, or medical record is involved -- this is a mechanism demo, not a validated prediction.

What this actually is, and its real limits

  • Not a clinical-NLP engine. This does not read raw, unstructured medical report text. It compares STRUCTURED fields (diagnosis, treatment plan, prognosis, recovery estimate, permanent impairment, work capacity) with a deterministic rule set -- stated plainly, not dressed up as an AI extraction capability that isn't built.
  • A real bug was found and fixed building this demo: an early version flagged any change in the diagnosis text as material, which fired on purely benign restatements ("ankle sprain, grade 2" → "...resolved"). Fixed by making diagnosis-text-change informational only -- it's reported, but only counts toward "material" alongside a real objective severity signal (escalated treatment, worsened prognosis, or downgraded work capacity). See change_signal_engine.py for the full before/after.
  • Competitive check, done live before building: Wisedocs documents real within-record inconsistency detection; EvolutionIQ's MedHub (a real $730M CCC Intelligent Solutions acquisition) documents real point-in-time medical synthesis and "next best action" guidance. Neither vendor's own public material documents comparing successive assessments over time and tying a specific detected change to a specific generated action -- the best available public evidence, not proof they don't do this privately.
  • Real next step: 6 real cases is a proof of concept, not a validation sample. Scaling further by hand hit a real, measured ceiling -- see below. Reaching 25-50 needs a real LLM-extraction layer over the full WCAB corpus, not more manual reading. Real managing-agent claim files, specifically, are only available once accepted into Lloyd's Accelerator (checked live -- no pre-application path exists).
  • Every generated action requires human approval. This never independently changes a reserve or makes a medical/legal determination.

Validated against 7 real cases -- and a real feasibility check on scaling further

Real managing-agent claims data is only available DURING Lloyd's 10-week Accelerator, after a mutual NDA -- checked live, no pre-application path exists. A genuine free alternative does: California's WCAB publishes every panel decision as a real PDF, no login or fee -- 5,884 for 2026 alone. Asked to scale this to 25-50, we read 196 real decisions and landed at 6, not 25-50 (~5-15% hit rate -- most are legal/procedural disputes, not clinical trajectories). Then asked whether LLM extraction could unlock the rest: no API key is set in this environment for a standalone script, but that was never the real bottleneck -- Claude reads and extracts these directly, no separate API call needed, which is how every case here was actually produced. Tested this concretely on a fresh, non-overlapping batch of 59 more decisions using a faster digest-based triage: same ~5-15% hit rate. That confirms corpus composition, not extraction technology, is the real ceiling -- one more real case (O'Brien, a genuine apportionment-shift boundary case) came out of it.
