Not another dashboard

Ten unrelated accounts, all quietly exposed to the same thing at once.

No single account's file shows that. Upload your book of insureds and this cross-references every one of them, by name, against every real emerging-risk signal Nubuye tracks — SEC 10-K risk-factor language, material 8-K filings, cyber-incident disclosures, real litigation dockets — and surfaces only the cases where more than one account in this specific book is independently exposed to the same category right now. That's the accumulation a market event is made of, found before the market finds it.

Upload a book of insureds

One insured per line, comma-separated: insured_name,policy_ref. The first line can be a header row (auto-detected) or omitted. Each name is checked against the same real sources Submission Auto-Check uses — see the caveats below for exactly how matching works and where it can miss.

What this actually changes, and what it doesn't

Stated honestly, same discipline as every other tool on this site:

  • This is checkSubmission — the same engine Submission Auto-Check already runs one account at a time — looped over a whole book, client-side, then grouped by risk category across accounts. No new data source, no new matching logic; the new thing is looking ACROSS accounts for where the same category hits more than one of them, which no single-account tool, including this project's own, ever surfaces.
  • A cluster only shows here when 2 or more insureds in this specific uploaded book independently match the same category. One account alone matching a category is real but isn't accumulation — it's listed separately, not folded into a cluster.
  • Matching is substring-based on a normalized legal name (same as every other check in this engine) — an unlisted subsidiary, a DBA, or a materially different legal name won't match. Zero matches means nothing was found under this exact name, not "cleared."
  • CSV parsing here is intentionally simple (comma-split, no quoted-field support) — a real bordereau ingest would need a proper CSV/Excel parser. Stated, not hidden.
  • This is not wired to the daily automated refresh yet — that pipeline currently only republishes moat_export.json itself and the Claim Watchlist subscription feed (see Book Monitor), and that site-publish step still has an open, unresolved bug of its own. A "subscribed portfolio" that re-checks your book every day, the same way Book Monitor's claim list does, is the obvious next step once that's solid, not before.
  • A cluster is a concentration signal, not a legal conclusion — it does not mean these insureds share a common claim, are liable, or are connected to each other in any way beyond independently showing up in the same real, dated disclosure category.
