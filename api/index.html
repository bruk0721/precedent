For developers: this isn't just a browser lookup

The interactive checks on this site run entirely client-side, by design — nothing you type into them ever leaves your browser. But every tool also has a real server-side API behind it, built for exactly what an enterprise underwriting or claims workflow actually needs: batch processing and standing subscriptions, not one-by-one manual checks.

Batch

Run a whole book of business in one call

Don't want to hand-build the request body? Upload a bordereau CSV directly and get a results CSV back -- the same batch endpoint below, with the file handling done for you.

Each tool has a batch endpoint that takes a real list of accounts, claims, or facilities and returns every result in one response — the real shape of a nightly bordereau run, not a form a person fills in one at a time.

EndpointMax per callWhy
/v1/claim-watchlist-check-batch500Reads a pre-computed snapshot — fast
/v1/firefighter-presumption-pricing-batch500Same — a full treaty's ceding-company list in one call

  -H "Content-Type: application/json" \
  -d '{"departments": [{"state": "CO", "dept_name": "Colorado Springs"}]}'
Subscriptions

Submit your book once. Get alerted automatically.

Every tool also has a standing-subscription watcher: submit your open claims, insured facilities, or deal pipeline once, and it gets re-checked automatically on every data refresh — new matches only, never a duplicate alert. That's the real workflow-lock-in answer: nobody re-pastes a name into a web form.

Point-in-time

What did the record show on the date you bound?

The Disclosure Auditor's as_of_date field replays the audit against a past date instead of right now — the real question an underwriter or claims handler asks after the fact. How exact that replay is depends on what each source actually exposes:

SourcePrecisionHow
OSHAExactReal inspection-open date on each citation; excludes anything opened after the cutoff.
USAspendingExactReal award Start Date; excludes anything that hadn't started yet.
EPA ECHOQuarter-resolution, estimated boundariesECHO's own rolling 12/13-quarter compliance-history strings (one character per quarter). Quarter boundaries are estimated by counting backward from today, not read from ECHO's own boundary metadata -- disclosed every time this is used, not assumed exact.
curl -X POST https://<your-deployment>/v1/disclosure-schedule-audit \
  -H "Content-Type: application/json" \
  -d '{"company_name": "Chemours Company", "as_of_date": "2024-06-30"}'
Any real company

Pull any public company's real subsidiary list, live, on demand

The Underwriter Console's entity-resolution crosswalk only pre-covers the curated PFAS/AFFF defendant list. This instead pulls a real, current SEC Exhibit 21 at request time for literally any public filer — confirmed live against companies this project never curated at all (Workday, Procter & Gamble). Two real filer-format gaps are handled honestly, not silently dropped: a subsidiary list split across multiple HTML tables in the same document (DuPont), and a filer whose Exhibit 21 isn't a table at all (Essential Utilities, via Certent Disclosure Management) — that one returns a clear reason and a link to the real filing instead of a fabricated empty list.

curl -X POST https://<your-deployment>/v1/subsidiary-lookup \
  -H "Content-Type: application/json" \
  -d '{"company": "Procter & Gamble"}'
Accumulation

Screen a corporate family for hidden risk concentration

A clean Exhibit 21 pull answers "who are this company's real subsidiaries," not "does this family concentrate exposure to the same real hazard across sibling entities an underwriter would never think to cross-reference by hand." This endpoint pulls the real subsidiary tree, then runs the same live EPA ECHO + OSHA checks the Disclosure Auditor uses against every screened entity (parent + up to 11 subsidiaries, to keep a single request's live-call count bounded), and rolls the results into a concentration view. Honest limits: SEC filers only, capped entity count per request, and EPA ECHO's own published throttle (300 calls/hour per caller) can trip mid-screen on a busy hour — reported per-entity when it happens, not hidden.

curl -X POST https://<your-deployment>/v1/subsidiary-accumulation-screen \
  -H "Content-Type: application/json" \
  -d '{"company": "Chemours"}'
PFAS

Check a corporate family against real PFAS manufacture, import, and release data

Same subsidiary-tree pattern as the accumulation screen, swapped onto EPA's real PFAS Analytic Tools FeatureServer (a separate, keyless public ArcGIS service -- not subject to ECHO's throttle) instead of EPA ECHO/OSHA: TRI on-site PFAS releases by real parent-company name, and TSCA Chemical Data Reporting PFAS manufacture/import by real facility name. Confirmed live against Chemours -- its parent entity alone returned 10 real TRI releases (HCFC-124, named facilities including Louisville Packaging and the Gregory, TX site) and 10 real TSCA CDR rows naming Chambers Works, Fayetteville Works, and Washington Works. Honest gap: EPA CompTox/CTX chemical-hazard scoring and UCMR 5 drinking-water data were both named in the research behind this endpoint but aren't wired in yet -- see not_checked in the response.

curl -X POST https://<your-deployment>/v1/pfas-exposure-monitor \
  -H "Content-Type: application/json" \
  -d '{"company": "Chemours"}'
Category sweep

Is a whole product category's CPSC recall rate accelerating?

Different shape from everything above: not a named manufacturer or company, but a free-text category or keyword, checked against CPSC's real, live, keyless Recall API across two adjacent time windows. Confirmed live: "lithium battery" over the trailing year returned real recalls (Bose battery packs, Ororo heated-jacket battery packs, among others) with a computed window-over-window ratio. Honest scope: this is recall-level velocity, not the pre-recall complaint-level signal SaferProducts.gov's OData incident API would give -- that API returned a confirmed HTTP 401 without a free CPSC-issued key while building this, so it isn't wired in yet. NHTSA is left out entirely: its real complaints API needs an exact vehicle make/model/modelYear, not a category sweep. A battery/micromobility keyword automatically surfaces CPSC's own acknowledged lithium-ion taxonomy gap.

curl -X POST https://<your-deployment>/v1/cpsc-recall-velocity \
  -H "Content-Type: application/json" \
  -d '{"keyword": "lithium battery", "window_days": 365}'
Built, unverified

Is a mass tort's real federal filing rate accelerating?

Same recent-vs-prior-window shape as the CPSC feed above, aimed at CourtListener/RECAP's real federal MDL dockets under the JPML court instead. This is the one endpoint on this site that could not be confirmed against a real response before shipping: CourtListener requires a free, user-registered API token for every endpoint, including anonymous read-only search, which returned a confirmed HTTP 401 while building this. Set COURTLISTENER_API_TOKEN (free at courtlistener.com/profile/api-token) to actually run it; without it, the endpoint returns an honest skipped response rather than fabricating a result. Built against CourtListener's documented v4 schema (double-underscore range lookups, a real date_filed field, a court= filter), but the exact date_filed__gte/__lte syntax and the "jpml" court-id slug were not individually confirmed live.

curl -X POST https://<your-deployment>/v1/mdl-docket-tracker \
  -H "Content-Type: application/json" \
  -d '{"keyword": "AFFF", "window_days": 180}'
Honest status

What's real today, and what isn't yet

All of the above is working, tested code today — not a roadmap slide. What it is NOT yet: deployed to a public production URL, or wired into email/Slack notifications (no mail or webhook credential exists in this environment yet). There is also no audit-trail export into a specific underwriting workbench (Charles Taylor InsureTech, Whitespace, DXC, etc.) — every response here is already structured JSON with a real source URL per finding, which is the real precondition for that integration, but the integration itself needs a real platform and credentials we don't have in this environment. The batch, subscription, and point-in-time logic itself is real and already running against live government data; standing it up as a hosted, authenticated production API with a workbench connector is the real next step, not a claim this page is making ahead of it.

ChangeSignal is not in this table. It's a local rule-based engine (see change_signal_engine.py), not yet wired into this API backend as a batch or subscription endpoint — stated plainly rather than implied by omission.
