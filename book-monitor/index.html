Not another dashboard

Stop checking one claim at a time.

Every other tool on this site checks a single claim because that's the demo-friendly shape. A real claims desk doesn't have one open claim, it has a book. Upload the whole thing. This runs every row through the same real federal cross-match as Claim Watchlist, then shows you only the rows that are sitting on an active cluster — not the whole book re-read back to you.

Upload an open-claims book

One claim per line, comma-separated: claim_id,manufacturer,model_or_identifier. The first line can be a header row (auto-detected) or omitted. This checks every row against the same real defect_velocity_clusters table as Claim Watchlist — CPSC, openFDA MAUDE, and NHTSA ODI.

What this actually changes, and what it doesn't

Stated honestly, same discipline as every other tool on this site:

  • This is the same checkClaimWatchlist logic as the single-claim page, just looped over every row in the book, client-side. No new data source, no new matching logic -- only the delivery shape changes.
  • CSV parsing here is intentionally simple (comma-split, no quoted-field support) -- a real bordereau ingest would need a proper CSV/Excel parser. Stated, not hidden.
  • This still runs on a button click, not on a schedule -- a real "book monitor" would re-run this automatically (daily, against a stored book) and only notify on a new flag since the last run. That's the real next step, not yet built: see the Claim Watchlist page's batch API and claim_watchlist_subscriptions.py in the private pipelines repo, which already re-checks a subscribed book daily and diffs against the prior run -- this page is the same underlying engine, manually triggered, so you can see the digest shape without needing the daily job wired to this UI yet.
  • A match means the manufacturer+model is sitting on a real, currently-tracked federal complaint-velocity cluster -- not a legal conclusion that this specific claim is part of it.
