What this actually changes, and what it doesn't

Stated honestly, same discipline as every other tool on this site:

  • This is the same checkClaimWatchlist logic as the single-claim page, just looped over every row in the book, client-side. No new data source, no new matching logic -- only the delivery shape changes.
  • CSV parsing here is intentionally simple (comma-split, no quoted-field support) -- a real bordereau ingest would need a proper CSV/Excel parser. Stated, not hidden.
  • The "Subscribed book" panel above reads two files a GitHub Actions workflow publishes daily from the private pipelines repo: the subscription list itself, and an append-only alert log stamped with when Nubuye first noticed each match (claim_watchlist_subscriptions.py). A row tagged NEW was newly detected within the last 2 days; everything else was already known as of a prior run -- that's the actual diff, not just "re-run the same check and show it again."
  • The subscription list itself is still the illustrative 3-claim demo list from that script, not a real bordereau intake form -- subscribing a real book means adding rows to that file (or, eventually, an upload form that writes to it), not something this page can do yet.
  • No notification channel is wired to the alert log (no email/Slack credential exists in this environment) -- same disclosed gap as every other subscription engine in this project. You have to come look at this page; it doesn't yet come find you. That's the honest remaining gap between this and a real FloodFlash-style push.
  • The paste-a-CSV flow below this is still here for a one-off book that isn't on a standing subscription -- same underlying engine, just not rechecked daily.
  • A match means the manufacturer+model is sitting on a real, currently-tracked federal complaint-velocity cluster -- not a legal conclusion that this specific claim is part of it.
